오늘의 실무 산출물

프롬프트 템플릿이 아닙니다.
'현장 도메인 지식 정의서'입니다

프롬프트 문장은 언제든 바뀝니다. 진짜 중요한 것은 "우리 부서가 무엇을 중요하게 보고, 무엇을 거르는가"라는 현장 기준을 언어화하는 것입니다.

💡 핵심 명제:
도메인 지식이 없는 프롬프트는 껍데기에 불과하며, 도메인 지식이 담긴 기준은 에이전트의 영구 스킬이 됩니다.
[실습 양식] 우리 부서 현장 도메인 지식 정의서
배포 워크시트 1페이지 · 강의 중 실습 작성
1현장 경중 판단 기준 (즉시 조치 / 일정 계획 / 단순 기록)
2원문 대조 필수 검증점 (규정 조항 · 핵심 수치 · 설비 상태)
3사내 보안 경계선 (외부 전송 금지 데이터 및 마스킹 규격)
4에이전트 스킬(SKILL.md)로 영구 보존할 부서 매뉴얼
프롬프트를 외우는 것이 아니라 부서의 도메인 지식을 문서화하는 것이 오늘 산출물입니다.

실무자의 진짜 역할

프롬프트 타이핑을 치는 사람이 아니라,
현장 지식을 정의하고 검증하는 지휘자

1

도메인 지식 언어화

베테랑 실무자의 머릿속에만 있던 현장 판단 기준과 우선순위를 명확한 규칙으로 정의합니다.

2

검증 하네스 통제

AI의 출력을 맹신하지 않고, 사내 규정 원본과 대조(Cross-check)하는 안전 검증선을 구축합니다.

3

스킬 자산화 구축

일회성 채팅으로 날리지 않고, 팀원 누구나 재사용할 수 있는 표준 스킬 파일(SKILL.md)로 시스템화합니다.

실무자의 가치는 프롬프트 테크닉이 아닌 도메인 지식과 검증에 있습니다.

프롬프트 강의를 백날 들어도 실무에 안 쓰이는 이유

"프롬프트 작성법, 템플릿 열심히 배웠는데...
결국 실무에선 뻔한 교과서 답변만 나옵니다."
착각: "프롬프트를 못 써서 그렇다?"

아닙니다. 프롬프트 문장을 아무리 화려하게 다듬어도, 모델은 한국전력공사의 사내 맥락과 현장 실무 기준을 모르면 인터넷 상식만 읊을 수밖에 없습니다.

진실: 이미 해결된 기술 vs 진짜 병목

프롬프트 문안 작성은 멀티턴 대화와 스킬 파일로 이미 해결되었습니다. 진짜 병목은 "현장의 도메인 지식이 모델에게 주입되지 않은 것"입니다.

프롬프트 작성 요령에 매달리는 것이 왜 시간 낭비인지 짚습니다.

기술의 현주소

프롬프트 엔지니어링은 이미 끝난 문제입니다

과거의 방식 (일회성 프롬프트 집착)
수십 줄짜리 프롬프트를 매번 복사·붙여넣기
→ 창 닫으면 날아가고, 수정할 때마다 문장 전체를 다시 손봐야 하는 극심한 비효율.
현재의 방식 (멀티턴 & 스킬 자산화)
도메인 지식을 스킬 파일로 저장하고 멀티턴으로 조율
→ 부서 규칙(Context)과 매뉴얼(Skill)을 파일로 한 번 장착하면, 대화 몇 번으로 완벽하게 수렴.
프롬프트 엔지니어링에 매달리는 대신 스킬과 도메인 지식으로 넘어가야 합니다.
🔴 라이브 사례 · 현장 순시 메모

거친 현장 메모: 무엇이 좋은 보고서를 만드는가?

3호 변압기 쪽 소리 좀 이상함. 웅- 하는 소리가 평소보다 큼. 2호 피더 케이블 피복 약간 긁힘 흔적 있음. 당장 문제는 없어 보임. 동관 2층 분전반 정기점검 완료. 이상 무. 변전실 환풍기 먼지 많이 쌓여서 소음 심함. 청소 필요.

"이걸 보고서로 요약해 줘"라고만 하면 AI는 4개를 나열할 뿐입니다. 무엇이 빠졌을까요?

메모를 보고서로 만드는 과정에서 드러나는 도메인 지식의 실체를 확인합니다.

비교 검증

차이를 만든 것은 프롬프트가 아니라 '현장 도메인 지식'

프롬프트 문장 (단순 그릇)

"보고서 형태로 요약해 줘"
"3문단으로 간결하게 작성해 줘"

→ 아무리 공손하고 자세히 써도 변압기 이상음의 심각성을 모르면 일반 요약에 그침.

주입된 도메인 지식 (실제 본체)
우선순위변압기 이상음 = [즉시] 조치 (단선 및 정전 위험)
계획수립케이블 피복 = [계획] 조치 (주간 정기보수 반영)
단순기록환풍기 청소 = [기록] (당일 결재 불필요)
차이를 만든 본체는 프롬프트가 아니라 실무자의 도메인 지식입니다.

프롬프트 테크닉을 공부하지 마십시오. 이미 모델과 멀티턴 기술이 알아서 알아듣습니다.
실무자가 해야 할 유일한 일은 현장의 판단 기준을 명확한 언어로 정의하는 것입니다.

프롬프트 공부를 멈추고 도메인 지식 정의에 집중해야 함을 강조합니다.

프롬프트 반복의 비효율

매번 프롬프트를 새로 치는 것은 가장 비효율적인 방식입니다

프롬프트 반복 입력의 낭비
  • 매주 월요일마다 메모장에 적어둔 프롬프트를 다시 찾아 복사합니다.
  • 담당자가 바뀌면 그동안 공들여 만든 프롬프트 노하우가 함께 사라집니다.
  • 텍스트 답변만 줄 뿐, 실제 사내 엑셀이나 브라우저 작업을 대신하지 못합니다.
스킬 파일(SKILL.md) 기반의 자산화
  • 현장 도메인 지식을 '스킬 파일'로 한 번만 작성해 둡니다.
  • 후임자에게 파일 하나만 넘겨주면 인수인계가 100% 완료됩니다.
  • 에이전트가 로컬 파일, 웹 브라우저를 직접 조작해 결과물을 완수합니다.
프롬프트 휘발성을 극복하고 스킬로 남겨야 하는 이유입니다.

비유로 이해하기

남이 지은 식당(SaaS) vs 우리 집 주방(로컬 에이전트)

외부 SaaS정해진 메뉴만 주문 가능. 사내 고유 데이터를 가져가서 조리할 수 없음.
로컬 에이전트사내 PC 환경에서 부서의 고유 데이터와 매뉴얼을 직접 결합하여 맞춤 조리.
외부 챗봇 서비스와 사내 로컬 주방 환경의 차이를 설명합니다.

도입 검토 기준

사내 자동화 도입 시 반드시 던져야 할 3대 질문

1. 데이터 격리

외부 클라우드 전송 없이 사내 로컬 PC 인프라 내에서 안전하게 처리되는가?

2. 실무 도구 실행

글자 출력에 머무르지 않고, 사내 파일·엑셀·웹 브라우저를 직접 제어하는가?

3. 도메인 지식 축적

휘발되지 않고 팀원 및 후임자에게 인수인계 가능한 스킬 자산으로 축적되는가?

🔴 라이브 시연 ⑥ · 자가 치유

오류 발생 시 에이전트의 자가 치유(Self-healing)

Self-healing 루프의 동작 과정

1. 명령 실행 중 예외 오류 발생
2. 에이전트가 중단되지 않고 터미널 에러 로그를 스스로 분석
3. 원인 파악 후 수정 코드를 작성하여 스스로 재실행
4. 합격 조건 충족 시 최종 완료 보고

"사람이 오류를 수동으로 고치는 것이 아니라, 오류를 보고 고치는 루프를 에이전트에게 줍니다."

오류를 스스로 해결하는 에이전트의 자가 치유 루프를 확인합니다.

현업 복귀 후 즉시 적용 가능한 우선 구축 스킬 3선

A
주간업무 실적 취합

팀원별 메모 5건을 부서 표준 양식 1장으로 가공. 합격 조건: 3문단 구성, 수치 근거 명시, 표준 경어체 통일.

기획 · 관리 부서
B
민원 답변 초안 작성

민원 유형별 필수 안내 항목과 공문 표준 톤을 스킬 매뉴얼로 표준화. 실무자는 최종 사실관계 검수만 수행.

고객 · 영업 부서
C
규정 신구 조문 대조표

개정 전·후 규정을 나란히 대조하고 변경 조항을 자동 비교 표기. 검증 조건: 조항 누락 0건.
